# Проверка требований ДЗ 4

Дата: 2 октября 2026. Предмет проверки — отдельное приложение хромакея, а не ДЗ 16.

| Требование преподавателя | Реализация | Проверка |
|---|---|---|
| Выбор видеозаписи | Файловая загрузка через браузер, проверка ffprobe | Учебный MP4; синтетические MP4/MOV/WebM/AVI; отказ для битого файла и аудио без видео |
| Задание удаляемого фона через HEX или пипетку | Оба способа плюс цветовая палитра | Выбор пикселя исходного кадра, ручной HEX; неверный HEX отклоняется |
| Удаление выбранного фона | FFmpeg chromakey с альфа-маской | Проверка пикселей зелёного и синего фона, сохранение красного объекта; реальные кадры датасета |
| Замена на изображение или цвет | Два режима; масштабирование и центральная обрезка фонового изображения | Пиксели нового цвета и картинки проверены автоматически; оба режима проверены на учебном ролике |
| Итоговое видео и скачивание | H.264 MP4, AAC при наличии аудио; Content-Disposition attachment | Декодирование MP4, длительность, разрешение, звук; полный файл и HTTP Range 206 |
| Выбор цвета хромакея | HEX, палитра, пипетка | Зелёный, синий и ручной цвет с учебного кадра |
| Параметры кеинга | Допуск цвета, мягкость края, подавление зелёного/синего отблеска | Отдельные тесты доказывают изменение реальных пикселей при изменении допуска и мягкости |
| Предпросмотр итогового видео | Плеер обработанного фрагмента и полного результата | Фрагмент до 5 секунд / 960 px; полный учебный ролик 10,2 секунды / 1280×720 |
| Веб-интерфейс и Docker | Flask, HTML/CSS/JS, отдельный Dockerfile и compose | Сборка образа, healthcheck, smoke реального FFmpeg внутри контейнера |

## Исправления после расширенного аудита

1. Частота кадров больше не зависит от типа нового фона: раньше цвет давал 30 fps, а картинка 25 fps. Оба режима используют среднюю частоту исходного видео, включая 24000/1001. Для переменной частоты получается постоянная средняя; вне диапазона 1–120 используется 30 fps.
2. Сохранено исходное смещение аудио относительно начала видеодорожки: задержка не пропадает. Проверен сигнал с полусекундной задержкой.
3. При истёкшем сроке хранения результата возвращается понятная ошибка 404 вместо внутренней ошибки 500.
4. Видео с неквадратными пикселями нормализуется без искажения отображаемых пропорций. Проверен SAR 2:1.
5. Значение допуска по умолчанию на сервере совпадает с интерфейсом: 0.045.
6. Неверный HEX неактивного цветового фона не мешает обработке в режиме изображения.
7. Новое видео активируется для обработки только после успешной загрузки его кадра; режим пипетки сбрасывается при смене видео.

## Проверки

`python -m pytest tests -q`: 20 тестов. Они генерируют собственные небольшие видео и проверяют результат FFmpeg, а не только коды ответа API. `node --check static/app.js`: проверка синтаксиса JavaScript.

Docker smoke проверяет фактические цвета пикселей, сохранение объекта, звук, длительность, получение готового MP4. GitHub Actions выполняет тесты и независимо собирает/проверяет образ на Linux; точный результат и SHA доступны во вкладке Actions репозитория.

## Ограничения и границы соответствия

- Лимиты приложения: до 256 МБ, 5 минут, 3840×2160 пикселей с дополнительным ограничением отображаемого размера для неквадратных пикселей; один рендер одновременно.
- Хромакей удаляет цвет, а не распознаёт объект: предмет выбранного цвета тоже исчезнет. Волосы, тонкие провода и смазанные границы могут обрабатываться неидеально. На учебном видео это заметно на проводах. Параметры нужно подбирать под съёмку.
- Пипетка работает с первым кадром; HEX позволяет задать любой другой цвет вручную. Автоматическое определение объекта и выбор произвольного кадра заданием не требовались.
- Проверены локальный ARM64 Docker и GitHub CI; это не обещание одинаковой скорости на всех компьютерах. Длительные 4K-видео не использовались для нагрузочного теста.
- Приложение предназначено для локального запуска. Нет авторизации и многопользовательского хранения. Файлы старше суток удаляются при следующей загрузке; задания сбрасываются при перезапуске.
- В общих условиях курса отдельно указано: код для проверки берут только из персонального репозитория GitLab МИЭМ. По просьбе пользователя эта работа опубликована в отдельном GitHub-репозитории. Наличие GitHub само по себе не выполняет требование сдачи через GitLab; публикация в нужный учебный GitLab должна быть выполнена отдельно.

- Все 20 pytest-тестов прошли; синтаксис JavaScript корректен. Docker smoke и `scripts/verify_unseen.py` также прошли.
- Через настоящий Chromium/Playwright загружены собственные видео: зелёный фон, красный объект и звук (6,2 с, 320×180, 24 fps); синий фон с красным объектом без звука (1,5 с). Создано отдельное жёлто-синее фоновое изображение.
- Пипетка проверена на масштабированном Canvas: выбранный HEX точно совпал с RGB соответствующего декодированного пикселя. Проверены ручной HEX, допуск, мягкость и оба режима подавления отблеска.
- Проверены ошибки битого исходника, неверного HEX, отсутствующего и битого фонового изображения. Изменение параметров скрывает скачивание устаревшего результата; новое исходное видео сбрасывает результат.
- Предпросмотр зелёного ролика длится 5 секунд, полная версия сохраняет длительность и звук. Скачанный результат действительно воспроизводился в Chromium, время воспроизведения увеличивалось.
- Замена цветом и изображением проверена через интерфейс и реальные пиксели скачанных MP4: новый фон присутствует, красный объект сохранён. Размер, 24 fps, длительность и наличие/отсутствие звука соответствуют входу.
- Учебный ролик обработан в трёх режимах: предпросмотр (960×540, 5 с), полная запись с цветом и с изображением (1280×720, 10,2 с). Кадр учебного результата просмотрен визуально: фон заменён; тонкие провода и края по-прежнему требуют подбора параметров, как описано в ограничениях.

Добавлен workflow `Verify published Docker image`: он скачивает именно опубликованный архив и Compose из релиза, проверяет SHA-256, выполняет `docker load`, запускает Compose с `--wait`, сравнивает исходники внутри образа с репозиторием и проверяет реальные видео через HTTP. Это отдельная проверка передаваемого образа, помимо сборки Dockerfile в обычном CI.
